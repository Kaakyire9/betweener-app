## Webhook delta and foreground fallback

Stream documents a stable **`X-Webhook-Id` header across retries**, separate from its event-body model. The local handler now hashes a versioned app/call/delivery identity into the existing digest primary key. A retry with changed formatting/body still maps to the same receipt. Missing headers preserve legacy raw-body hashing. No RPC/schema migration is needed.

Raw-body HMAC, exact Connect CID parsing, five-minute timestamp check, size cap, concurrent SQL insertion and GET-only reconciliation remain. The ID header is not separately authenticated by the body HMAC: it is a deduplication hint, never permission or media truth. Altering it can cause another bounded GET wakeup, not acceptance, token issuance or call creation. No unrelated push/Live handler changes are proposed.

A single **connect-webhook** deployment requires separate approval. Pin its complete dependency closure and preserve the original deployed closure for rollback; worker/shared push deployments are not required. Old raw-body receipts and new delivery receipts can coexist during rollout; one extra reconciliation wakeup is harmless. Historical evidence is not rewritten.

**Webhook delivery is optional for the first supervised foreground pilot.** The actual worker executes `rpc_connect_sweep`, claims durable work, reads current provider state and reconciles under database authority. The sweep revisits due sessions roughly every ten seconds; the five-second dispatch cadence and queue work add latency, not a guaranteed cutoff bound. Foreground clients poll canonical RPC state. Local tests exercise ACTIVE detection and cleanup with zero webhook receipts. A verified recurring schedule and supervised monitoring are mandatory; client polling alone is insufficient. Provider GET behavior during a real session remains a pilot observation, not an offline attestation.
