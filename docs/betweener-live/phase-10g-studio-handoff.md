# Phase 10G - Betweener Studio readiness

This is the exact Phase 10F handoff. Phase 10F contains no Studio UI.

1. **Current controller-source model.** `live_odo_show_sessions.control_source` is the closed set `odo | mobile_host | studio_host | system`. Human controller sources require a user; Odo/System do not.
2. **Current controller lease/fencing.** Odo uses `live_odo_session_state.lease_owner`, `lease_expires_at`, and monotonic `lease_generation/state_version`. Show control also has `control_lease_expires_at`; expired human control recovers through maintenance.
3. **Current Director Event protocol.** `live_director_events` is ordered per session by `sequence`, carries schema/state versions, a bounded typed payload, visibility, expiry, action/idempotency IDs, and a `source`. `live_director_updates` is the Realtime wake projection.
4. **Current Director snapshot structure.** `rpc_get_live_odo_system_program_snapshot_v1` returns session, controller, show, Quick Connect aggregates, music, Audience Pulse, Director sequence, lifecycle, and an aggregate safety summary. It excludes rosters, compatibility edges, ballots, prompts, and private decisions.
5. **Current Show State.** Phase 10E states remain authoritative: opening, host/pool focus, pair forming/active, post-pair, Pulse/topic/Odo Stage/intermission, low liquidity, draining/closing, host/policy pause, and recovery.
6. **Current scene catalogue.** `host_focus`, `host_plus_pool`, `pool_focus`, `pair_forming`, `quick_connect_active`, `audience_pulse`, `conversation_topic`, `odo_stage`, `music_intermission`, `branded_intermission`, and `session_closing`.
7. **Current Program Source abstraction.** Programme-controller origin is `mobile | studio | system`. `program_output_source` separately models `host_camera | active_pair | quick_connect_pool | odo_stage | audience_pulse | branded_visual | screen_share`; screen share is reserved, not implemented.
8. **Current Quick Connect pool safe projection.** Existing snapshots expose state, waiting count, eligible count/pairs, active pairs, available slots, reconnecting count, and completed rounds. They do not expose the compatibility graph.
9. **Current AutoMatcher safe operational metrics.** The Show/Full Quick Connect snapshots expose waiting people, eligible pair count, active pair count, and completed rounds. Pair selection remains wholly inside the existing deterministic matcher.
10. **Current Odo state.** `live_odo_session_state` owns direction/autopilot state, scene, sequence, budget/lease fencing, pause reason, and next decision state. System sessions initialize Odo after Stream readiness.
11. **Current Show Director architecture.** A service-only deterministic reconciler observes Live/Quick Connect state, writes typed show actions/events, respects scene dwell and Host suppression, and never selects participants or mutates RTC membership.
12. **Current Music Engine abstraction.** Phase 10E uses a licensed server catalogue, per-session state, typed actions/events, signed playback grants, kill switches, region/license checks, and separate control authority.
13. **Current Music State.** Safe fields are status, track/playlist IDs, mood, requested/effective volume, programme start, offset, source, action/reason, and version. Media URLs remain short-lived service grants.
14. **Current audio-ducking architecture.** Conversation state deterministically ducks or stops approved programme music. Playback is currently restricted away from publisher devices to avoid microphone feedback; there is no server-side mixer.
15. **Current Stream RTC architecture.** Server Edge Functions create Stream calls and server users; clients receive scoped tokens through existing admission functions. Phase 10F creates one deterministic Stream call after quorum and explicitly ends it during cleanup.
16. **Current authentication/capability model.** Mobile calls use Supabase user JWTs and server RPC capability checks. Worker operations are service-role-only. Admin/Studio-safe reads require an internal admin or service role. Never expose the service role to a browser.
17. **Current system-owned session model.** `live_sessions.ownership_type = system` plus allowlisted `system_session_kind` permits null creator IDs only for constrained Always-On Quick Connect sessions. No fake Supabase Odo account exists.
18. **Existing manual takeover operations.** `rpc_take_over_live_odo_v1` and `rpc_take_over_live_odo_show_v1` pause/release Odo while keeping the Live, RTC, matcher, music state, and Show Director records intact. The actor must be an authorized admin/Host and satisfy internal rollout access.
19. **Existing Resume Odo operation.** `rpc_resume_live_odo_autopilot_v1`, `rpc_resume_live_odo_full_quick_connect_v1`, and `rpc_resume_live_odo_show_v1` restore bounded automation after policy/Host checks without recreating providers.
20. **What is currently mobile-specific.** Expo Router navigation, React Native components, AppState refresh, Expo notifications, Stream React Native video/audio rendering, tactile controls, and mobile media permission flows.
21. **Which Live domain types should be shared with Studio.** Extract Director events/snapshots, controller sources, Show states/scenes, programme output sources, Quick Connect aggregate projections, Odo Full Quick state, music state/actions, Audience Pulse projections, versions, and reason codes.
22. **Which server RPCs/APIs are already browser-safe.** Read-only aggregate snapshots and typed admin RPCs are transport-safe over PostgREST with an authorized admin JWT. Provider/media endpoints remain server-only or capability-scoped. Browser-safe does not mean publicly callable.
23. **Which server APIs still assume mobile.** User media admission, notification wake/deep links, some Host flows, and playback/device policy are coupled to Expo/React Native behavior. Existing repository methods also import the mobile Supabase singleton.
24. **What would be required for browser webcam publishing.** A Studio web identity/capability, Stream React/WebRTC client integration, browser permission UX, scoped token admission, device selection, reconnect handling, and publisher telemetry.
25. **What would be required for browser microphone publishing.** The same scoped publisher admission plus device enumeration, gain/mute state, permission recovery, echo cancellation validation, output routing, and explicit live indicators.
26. **What would be required for screen sharing.** A capability-gated Stream screen-share track, the reserved `screen_share` programme output, explicit source switching, preview validation, browser capture UX, and Director events for start/stop/failure.
27. **What would be required for screen-share audio.** Browser-supported system-audio capture, separate audio-track policy, consent/indicator UX, mixing/ducking rules, provider compatibility checks, and deterministic fallback when capture is unavailable.
28. **What audio mixing architecture exists today.** There is no central audio mixer. Phase 10E distributes approved programme playback to eligible audience clients and avoids publisher-device playback; deterministic duck/stop state is server-authored.
29. **What long-term ProgramAudioMixer should look like.** A server/egress-side mixer should combine licensed programme audio and RTC programme sources, expose metering/ducking/fades, fence commands by controller generation, provide fail-silent recovery, and emit typed state/events.
30. **Current repository/workspace architecture.** The repository is one Expo/React Native application with feature modules under `features/live`, Expo routes under `app/live`, Supabase migrations/functions, shared `lib`, and Node regression tests. It is not currently a monorepo.
31. **Whether shared packages are practical.** Yes. Pure contracts, validators, reason codes, and controller state machines can move into a platform-neutral workspace package. React Native UI, Expo services, and native Stream adapters must remain application adapters.
32. **Recommended Phase 10G web technology based on actual repo.** Add a separate TypeScript React web app (Next.js is suitable) in a workspace, share only pure Live contracts, use Supabase Auth/PostgREST/Realtime and Stream's web SDK, and keep privileged orchestration in Edge Functions/RPCs.
33. **Security concerns for Studio.** Require phishing-resistant admin authentication, short sessions, explicit capabilities, server-side command validation, controller fencing/idempotency, audit trails, no service key in the browser, no raw compatibility/ballot/private content, and least-privilege Stream tokens.
34. **Controller-disconnect recovery requirements.** Studio must renew a bounded controller lease. On expiry, server maintenance must fail safe or return control to Odo according to policy, stop stale commands via generation/version checks, preserve RTC/matcher/music state, and surface recovery health.
35. **Exact blockers Phase 10G must solve.** Create the web workspace/shared package, browser auth and capability enrollment, Studio command RPCs with optimistic fencing, preview/program architecture, Stream webcam/mic/screen publishing, a real audio mixer, moderation console, controller heartbeat/recovery UX, operational dashboards, and full browser/device/security validation.
