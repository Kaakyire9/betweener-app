# Betweener v1.2.0 onboarding V2 rollout

This contract is additive. Do not remove or modify `profile-onboarding-submit`
or `rpc_service_complete_profile_onboarding_with_guard_v1` while v1.1.1 is
supported.

## Staging order

1. Apply `20260916120000_atomic_profile_onboarding_v2.sql`.
2. Deploy `profile-onboarding-submit-v2` with JWT verification enabled.
3. Run `supabase/verification/onboarding_v2_health.sql`.
4. Build/run the 1.2.0 client against staging.
5. Complete one Ghana and one global profile on separate test accounts.
6. Confirm each completion has exactly one receipt and 3-5 matching
   `profile_interests` rows.

## Device cases

- Kill and reopen the app on steps 3, 6, and 12; the draft and current step
  must resume.
- Go offline on the final step; the app must stay in onboarding and must not
  display the success state.
- Restore connectivity and retry; only one completion receipt may exist.
- Simulate a lost success response, retry with the same request ID, and confirm
  the receipt fast-path succeeds without invoking moderation again.
- Reject an avatar, replace it, then complete onboarding.
- Resume a legacy incomplete profile with an old avatar and confirm the user is
  asked to select it again so immutable approval provenance is created.
- Trigger a deterministic profile-text rejection and confirm the app returns
  to the relevant step.
- Change a Ghana region after selecting a locality and confirm all locality
  metadata is cleared.

## Production gate

Deploy only after staging device validation. Apply the migration before the
Edge Function. The 1.2.0 client must not be released until the V2 health script
is healthy and `profile-onboarding-submit-v2` is reachable.

Rollback is client-side: disable the 1.2.0 rollout. Keep the additive table,
function, and receipt data in place; do not route 1.2.0 completion back through
the legacy non-atomic client sequence.
