# Betweener 1.1.1 stabilization through 1.2.1

This checklist is the release contract for keeping installed 1.1.1 clients
healthy until 1.2.1 is adopted. Do not remove a compatibility path merely
because the current development client no longer uses it.

## Operating rules

- [ ] Run `supabase/verification/v1.1.1_production_health.sql` before and after every production database deployment.
- [ ] Use the project-pinned Supabase CLI 2.116.0 for database reset/push; older pinned versions cannot deploy concurrent-index migrations.
- [ ] Run the 1.1.1 compatibility and Guard database suites before every production database deployment.
- [ ] Use expand-and-contract migrations only: add before switching clients; remove only after the retirement gate.
- [ ] Keep production secrets server-side. Never place provider keys, service-role keys, tokens or raw moderation evidence in Sentry.
- [ ] Record the operator, deployment timestamp, migration range and health-check result in the release notes.
- [ ] Stop a deployment when any `release_blocker` count from the health script is non-zero.

## Phase B — deployment guardrails while 1.1.1 is supported

- [ ] Do not revoke authenticated `profiles` INSERT/UPDATE policies used by 1.1.1.
- [ ] Do not remove the guarded legacy UPSERT branch from `profile_guard_prevent_direct_public_text_write()`.
- [ ] Do not make a 1.1.1 profile field newly mandatory without a compatible default or adapter.
- [ ] Do not remove or rename columns, enum values, storage paths or RPC signatures used by 1.1.1.
- [ ] Version new RPC behaviour with a new function signature instead of changing an old client contract in place.
- [ ] Keep `profiles` schema/trigger locks in short fail-fast transactions; build large profile indexes concurrently in separate migrations.
- [ ] Run a rollback-only production canary after every profile/onboarding migration.
- [ ] Review Profile Guard and content moderation queues daily.
- [ ] Review provider-unavailable and timeout rates daily; operational failures must not restrict profiles.
- [ ] Review stuck attachment finalizations and retention worker failures daily.
- [ ] Keep the Guard operator configuration documented and verify unexpected `OFF` or `REPORT_ONLY` changes.

## Phase C — observability and incident response

- [ ] Alert on `PROFILE_GUARD_REQUIRED`, RLS failures and profile-write HTTP 4xx/5xx responses in Supabase Logs Explorer.
- [ ] Alert when a moderated profile remains discoverable.
- [ ] Alert when a hidden deterministic profile has no unresolved enforcement event.
- [ ] Alert when a `CLEAR` profile has an unresolved deterministic enforcement event.
- [ ] Alert when timeout-only image reviews enter `PENDING_REVIEW`.
- [ ] Alert when a chat attachment finalization remains claimed for more than 15 minutes.
- [ ] Add safe Sentry context to 1.2.1: error code, request ID, app version, platform and changed field names only.
- [ ] Maintain an incident runbook for Guard mode changes, review remediation and rollback.

Never log profile text, private-message text, phone numbers, access tokens,
signed storage URLs, encryption material or provider secrets.

## Phase D — prepare and release 1.2.1

- [x] Route normal profile edits through `profile-guard-update` in the 1.2.1 codebase.
- [x] Route onboarding completion through `profile-onboarding-submit` in the 1.2.1 codebase.
- [x] Remove unchanged fields before server moderation.
- [x] Keep onboarding completion atomic and idempotent.
- [ ] Complete the full 1.2.1 regression suite on iOS and Android.
- [ ] Verify 1.2.1 against production-compatible staging data and policies.
- [ ] Roll out gradually and monitor Guard, onboarding, profile-save and media funnels.
- [ ] Keep 1.1.1 compatibility enabled throughout rollout.
- [ ] Configure soft/force-update rules only after store availability is confirmed on both platforms.

## Phase E — retire 1.1.1 compatibility

All conditions are required:

- [ ] 1.2.1 is available in both stores.
- [ ] 1.2.1 adoption meets the agreed threshold for at least seven consecutive days.
- [ ] No supported client still uses direct profile UPSERT according to production telemetry.
- [ ] Profile-save, onboarding and media error rates are within the agreed baseline.
- [ ] Guard and content-review queues have no unexplained backlog.
- [ ] A rollback plan for the server-owned endpoints has been rehearsed.
- [ ] Product/operations explicitly approve the 1.1.1 retirement date.

Only after every condition is met:

- [ ] Raise the minimum supported version to 1.2.1.
- [ ] Revoke authenticated direct profile writes.
- [ ] Remove the legacy profile UPSERT compatibility branch.
- [ ] Retain historical moderation/audit records according to the retention policy.
- [ ] Run the final production health check and archive its output with the release record.

## Standard verification commands

```powershell
npx.cmd supabase --version
npx.cmd supabase test db supabase/tests/legacy_onboarding_guard_compatibility.sql
npx.cmd supabase test db supabase/tests/profile_contact_solicitation_guard.sql
npx.cmd supabase test db supabase/tests/content_safety_moderation.sql
npx.cmd supabase test db supabase/tests/view_once_pre_encryption_moderation.sql
npx.cmd supabase test db supabase/tests/profile_handle_lifecycle.sql
& 'C:\Program Files\PostgreSQL\16\bin\psql.exe' -v ON_ERROR_STOP=1 -f 'supabase/verification/v1.1.1_production_health.sql' 'postgresql://postgres:postgres@127.0.0.1:54322/postgres'
```

Run the production health script as a whole in the Supabase SQL Editor. The
current CLI Management API path prepares one statement at a time and rejects
multi-statement verification files.

The local database may report two `version_rule_release_blockers` when it has
no production iOS/Android `app_version_rules` seed rows. That is expected only
locally. Production requires both rules and must keep 1.1.1 at or above the
minimum supported version until Phase E.
